# Commit

변경사항을 논리적으로 나누어 바로 커밋한다. 커밋 요청 자체를 승인으로 간주하며, 별도의 승인 대기 없이 분석한 범위를 저장한다. 사용자가 명시하지 않은 변경을 되돌리거나 수정하지 않으며, `push`, `amend`, rebase는 별도 요청 없이는 하지 않는다.

## 절차

1. 저장소 상태와 변경 내용을 확인한다.
   - `git status --short`로 추적·스테이징·미추적 파일을 구분한다.
   - `git diff`, `git diff --staged`로 작업 트리와 스테이징 영역의 실제 변경을 각각 분석한다.
   - 필요하면 미추적 파일의 내용도 확인한다. 이 파일은 `git diff`에 나타나지 않으므로, 자동으로 포함하지 않는다.
   - 최근 커밋 제목을 확인해 저장소의 기존 메시지 관례를 참고한다.

2. 변경을 목적과 영향 범위가 독립적인 논리적 단위로 분류한다.
   - 서로 독립적으로 되돌리거나 검토할 수 있는 변경은 별도 커밋으로 제안한다.
   - 한 기능을 완성하는 데 필요한 코드·테스트·문서는 같은 커밋으로 묶는다.
   - 사용자 또는 다른 작업자가 만든 관련 없는 변경, 비밀 정보, 생성물, 대용량 파일은 범위에서 제외하고 이유를 알린다.

3. 각 단위에 한국어 Conventional Commit 제목을 만든다. 형식은 `feat: 요약`, `fix: 요약`, `refactor: 요약`, `chore: 요약` 중 알맞은 타입을 사용한다.
   - 요약은 명령형이 아닌 변경 결과를 짧고 구체적으로 표현한다.
   - 기존 프로젝트가 더 구체적인 관례를 사용하면 그 관례를 우선하되, 사용자가 요청한 타입 접두사는 유지한다.

4. 분류 결과에 맞춰 포함 파일과 제외 파일을 확인한 뒤, 제안한 메시지로 즉시 커밋한다. 별도 확인 절차나 대기 없이 진행한다.

5. 각 단위의 파일만 `git add`로 정확히 스테이징하고, 제안한 메시지로 `git commit`한다. 여러 커밋이면 단위별로 파일 범위를 다시 확인해 순서대로 만든다.

6. 완료 후 `git status --short`와 최근 커밋을 확인하고, 생성된 커밋 해시·메시지·남은 변경사항을 간단히 보고한다.

## 예외

- 변경사항이 없으면 커밋하지 말고 그 사실을 알린다.
- 이미 스테이징된 변경이 있어도 작업 트리 변경과 섞지 않는다. 분석한 논리적 단위에 따라 각각의 범위를 보존해 커밋한다.
- 검증이 가능하면 커밋 전에 관련 테스트나 정적 검사를 제안하거나 실행한다. 실패한 검증이나 실행하지 못한 검증은 커밋 보고에 명시한다.
